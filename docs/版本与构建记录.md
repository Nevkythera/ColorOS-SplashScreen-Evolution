## 固定构建命令

```bash
cd /tmp/cscr-build

# 1) 改版本号（versionCode +1）
sed -i 's/versionCode = N/versionCode = N+1/' app/build.gradle.kts

# 2) 编译
gradle :app:assembleRelease --offline

# 3) 对齐 + 签名（签名固定用 cscr-new.jks，详见 签名说明-SIGNING.md）
BT=/opt/android-sdk/build-tools/36.0.0
$BT/zipalign -f 4 app/build/outputs/apk/release/app-release-unsigned.apk /tmp/aligned.apk
$BT/apksigner sign --ks cscr-new.jks --ks-key-alias cscr \
  --ks-pass pass:<STORE_PASSWORD> --key-pass pass:<STORE_PASSWORD> \
  --out CSCR-<version>-release-<MMDD-HHMM>.apk /tmp/aligned.apk

# 4) 拷到 /workspace 并呈现给用户
```

## 其它长期约定

- ★ **包名规则（id33 起）**：`com.Nevkythera.ColorOSSplashScreenEvolution`
  （`Nevkythera` / `ColorOSSplashScreenEvolution` 含大写，`com` 小写）。
  **Android 包名允许大写字母**，Java 包名规范（JLS §6.1）也从未禁止大写 ——
  惯例全小写只是为了避开大小写不敏感文件系统的目录冲突（Windows/macOS 上
  `Foo` 与 `foo` 会撞成同一个目录）。因此：**包名本身合法，但源码目录必须保证
  同级没有任何"仅大小写不同"的兄弟目录**，否则 checkout 到 Windows/macOS 会互相覆盖。
  实测（id33）：`aapt dump badging` → `package: name='com.Nevkythera.ColorOSSplashScreenEvolution'`，
  构建/签名/安装全链路正常。
  包名迁移涉及 5 处必须同步（漏一处就装不上或模块不加载）：
  ① `app/build.gradle.kts` 的 `namespace` 与 `applicationId`；
  ② 源码目录 `app/src/main/java/<包路径>/`；③ 每个 `.kt` 的 `package` 与 `import`；
  ④ `AndroidManifest.xml` 的 `xposedid` meta-data；⑤ `java_init.list` 的入口类全限定名。
  另外 `module.prop` 的 `id=` 也要同步。
- ★ **内部代号是 `CSE`，不是 `CSCR`**（id33 起）：改版前叫 `CSCR`（COS Splash Screen Restore），
  包名迁移时统一改为 `CSE`。涉及 6 个位置，都是"日志/调试用"，不影响功能但影响排查：
  ① 日志 TAG（`CoSSplashModule`/`XposedRepo`/`SystemUiRestarter`/`MorphShapeView` 里 `"CSE"`）；
  ② 错误码前缀 `CSE-CL-001` / `CSE-SIG-001` / `CSE-FLD-001` / `CSE-HOOK-001`；
  ③ 视图 tag `cse_blur_bg` / `cse_morph_shape`（用于在 Splash 视图树里找装饰层）；
  ④ 远程偏好仓库名 `cse_prefs`（**App 侧与 Hook 侧必须同名**，
     分别在 `XposedRepo.REMOTE_PREFS_NAME` 与 `CoSSplashModule.REMOTE_PREFS_NAME`）；
  ⑤ 本地偏好文件名 `cse_config`（`CseConfig.PREFS_NAME`）；
  ⑥ 主题名 `Theme.CSE`（`themes.xml` 与 `AndroidManifest.xml`）。
- `java_init.list` 里写的是**源码全限定名**，但 R8 会在打包时把它重写成混淆后的短名
  （实测 id33 → `e4.n`，历史版本 → `f4.l`）。**这是正常行为，不要去"修复"它**；
  想确认映射是否正确，查 `mapping.txt` 里 `CoSSplashModule -> e4.n`。
- 作用域必须包含 `com.android.systemui` **和** `android`（系统框架，热启动 hook 需要），
  配置在 `app/src/main/resources/META-INF/xposed/scope.list`。
- 模糊 / 圆角装饰挂在 **wm.shell 的 `SplashscreenContentDrawer$SplashViewBuilder#build()`**
  （本 ROM 实测命中），framework 的 `android.window.SplashScreenView$Builder#build()` 不命中，
  仅作为双保险保留。
- 图标替换 / 缩小判定挂在 `SplashViewBuilder#createIconDrawable`（有 `mActivityInfo` 字段），
  `OplusShellStartingWindowManager#getIconExt` 在本 ROM 上不命中，不要再依赖它做主逻辑。
- **装饰类逻辑（模糊/圆角）里绝不能使用 install 期缓存的 Context**：
  `onPackageReady` 早于 Application 创建，`ActivityThread.currentApplication()` 返回 null。
  一律用 `splashScreenView.context`（运行期必然非空）。
- ColorOS 上 `android.window.SplashScreenView` **没有 override `onAttachedToWindow`**
  （日志 `splash_view_attached reason=method_not_found`），该出口在父类链中找不到时
  自动跳过，模糊兜底靠两个 build() 出口。
- 热启动 hook（`ActivityRecord#getStartingWindowType`）位于 services.jar，
  **必须**在 LSPosed 里勾选作用域「系统框架（android）」，否则模块根本不会加载进
  system_server（2026-09-13 13:05 日志实证：模块在 system_server 0 条记录）。
  勾上后**必须重启手机**（system_server 已运行，重启 SystemUI 不够）。
- 热启动 hook **只能装在 `onSystemServerStarting`**：`onPackageReady` 里按
  `packageName == "android"` 判断会在 SystemUI 进程误命中（SystemUI 会加载 "android"
  包来 inflate RemoteViews），用 SystemUI 的 ClassLoader 找 ActivityRecord 必然
  ClassNotFoundException。若要在 onPackageReady 兜底，必须先 `loadClass` 试探成功再装。
- **离线构建拿不到 `androidx.graphics:graphics-shapes` 的 aar**（缓存里只有 pom/module，
  Maven 也不通），所以 MD3E 指示器**无法使用官方 `RoundedPolygon`/`Morph`**，
  形状用极坐标谐波 `r(θ)=R·(1+Σaₖcos kθ)` 逼近官方 7 形状；
  **动画时序完全照抄** `androidx.compose.material3.LoadingIndicator.kt`：
  `GlobalRotationDurationMillis=4666`、`MorphIntervalMillis=650`、
  `spring(dampingRatio=0.6f, stiffness=200f)`、每完成一次形变旋转 +90°，
  旋转角 = `morphProgress*90 + morphRotationTarget + globalRotation`。
- ★ 更正（id29）：`graphics-shapes` 的 aar 其实**就在 gradle transform 缓存里**
  （material3 的传递依赖），显式 `implementation("androidx.graphics:graphics-shapes:1.0.1")`
  即可离线用官方 `RoundedPolygon`/`Morph`；官方形状序列用
  `LoadingIndicatorDefaults.IndeterminateIndicatorPolygons`（需
  `@OptIn(ExperimentalMaterial3ExpressiveApi::class)`）。谐波近似已废弃。
- ★ 官方形状坐标系实测（id30，用 JVM 探针直读官方库，比源码更可靠）：
  `IndeterminateIndicatorPolygons` 的 7 个形状坐标落在 **[0,1]×[0,1]**，几何中心
  **(0.5, 0.5)**；`RoundedPolygon.normalized()` 对它们是**幂等**的，不会把中心搬到原点。
  因此绘制时**必须减去形状固有中心**再平移到视图中心，否则形状会被推到右下角、
  旋转变成绕形状左上角（即"绕边缘转"）。
  另外形状质心与包围盒中心只差约 0.9px（100px 指示器），非对称不是偏心主因。
- ★ 不要再依赖 `Morph.calculateBounds()` 求中心：JVM 探针下它返回 [0,0,1,1] 正常，
  但真机（inline class ABI 差异）可能返回全 0，届时 `center=0` 会把形状甩到角落。
  现在用「全形状统一包围盒」：遍历 7 个形变对 × 11 个采样点的 `asCubics` anchor 点
  （anchor 是曲线真实经过的点，control 点会让包围盒虚胖），取全局 min/max，
  一次性静态计算，所有形状共用它 → 中心恒定、形变时不抖不跳。
- ★ **绝不要对"正在显示的 Drawable"调用会改 bounds 的方法**（id33 踩坑，直接导致
  SystemUI 崩溃 / 图标显示异常）：`GraphicUtils.drawable2Bitmap(drawable, 64)` 内部是
  `drawable.setBounds(0,0,64,64); drawable.draw(canvas)` —— 它**会把这个 64px 的 bounds
  留在原 Drawable 上**。若传入的是桌面图标（通常是 `AdaptiveIconDrawable`），图标当场
  被缩成 64px 画坏；若被多线程同时访问还会引发崩溃。
  取色场景必须用 `GraphicUtils.toSampleBitmap()`：在独立画布上绘制，**绘制前保存、
  绘制后还原** bounds/alpha/colorFilter，并且不回传原 bitmap。
  通用教训：**任何"为了分析而绘制"的操作都要 be side-effect free**，尤其是共享的
  Drawable / Bitmap。
- ★ **装饰层的位置不能只在首次布局算一次**（id33）：`alignToIconCenter` 原来用一次性
  `OnPreDrawListener`，横竖屏切换 / 分屏 / ROM 二次布局后 margin 不再更新，横屏启动时
  指示器就偏了。改为挂 `View.OnLayoutChangeListener` 到图标上持续跟随，并在
  target detach 时注销；`OnPreDrawListener` 仅保留作首次布局兜底。
  另外加"参数无变化就跳过"判断，避免无谓的 requestLayout。
- ★ **异步染色务必做三重防护**（id33）：后台线程只做纯计算（`iconAccentColor` 里
  `runCatching` 兜住全部异常，避免线程池线程死掉）；染色一律 `view.post` 回主线程；
  post 前校验 `isAttachedToWindow`，防止给已 detach 的旧 Splash 视图设色。
- ★ **旋转稳定性取决于质心，不取决于包围盒中心**（id32）：官方 7 形状的包围盒中心
  都是 (0.5,0.5)，但质心不是 —— Pentagon 质心偏下约 3%（顶点朝上、底边朝下），
  绕包围盒中心转时质心画圆，用户描述"只有五边形歪，其他图形正常"（其余形状
  近似对称，质心≈包围盒中心，所以看不出来）。**修法是每帧对当前实际形状算实时
  质心并钉在旋转轴上**，任意时刻残差恒为 0。
  教训：**不要预计算质心** —— raw `RoundedPolygon.getCubics()` 的质心 ≠
  `Morph.asCubics()` 顶点匹配后的实际质心（实测 Pill/Cookie4 残差 1~1.5px，
  因为 Morph 会重排 cubic 序列）。要么每帧实时算（最终方案），要么用
  `MORPHS[i].asCubics(0)` 的质心（但同一形状在相邻两个 Morph 里匹配不同，
  衔接处会跳变）。
  副作用提示：质心对齐后形变过程中形状会轻微"游走"（相邻形状质心差最大约 4%，
  100px 视图上约 2px），但是平滑连续的，远优于旋转甩动。
- **装饰层（指示器 / 模糊）必须对齐「图标中心」而不是「SplashScreenView 中心」**（id31）：
  `gravity = Gravity.CENTER` 把装饰放到 SplashScreenView 正中，但图标未必在那儿 ——
  底部品牌图（branding）、图标缩放、各 ROM 对 splash 布局的改动都会让图标整体偏移，
  表现为"指示器/模糊层相对图标偏心"。正确做法：找到图标 View，用
  `getLocationOnScreen` 分别取 parent 与图标的屏幕坐标相减，得到图标中心在 parent
  坐标系的位置，再用 `FrameLayout.LayoutParams` 的 **`gravity = TOP|LEFT` + `leftMargin/topMargin`**
  定位（margin 的参考点是左上角，gravity 不设成 TOP|LEFT 会算错）。
  注意 addView 时 View 尚未 measure（width/height 为 0），必须挂在
  `ViewTreeObserver.OnPreDrawListener` 上等布局完成再算，否则拿到 0 坐标。
  兜底：拿不到图标 View 或 10 帧后仍未布局完成，就保持 CENTER 不变。
- `MorphShapeView` 的 companion object 属性**按声明顺序初始化**，被依赖的
  （如 `BOUND_SAMPLES`）必须写在引用者（`SHAPE_BOUNDS`）之前，否则运行时 NPE。
- **网络状况（id30 复测）**：Google / Maven Central / GitHub raw / android.googlesource
  直连全部超时；但 **Maven 镜像可用** —— `https://maven.aliyun.com/repository/google/...`
  与 `https://mirrors.tencent.com/nexus/repository/maven-public/...` 均返回 200。
  注意 `androidx.graphics:graphics-shapes` 是 KMP 库，`graphics-shapes-1.0.1.aar`
  只是 4.5KB 空壳（仅 manifest + LICENSE，无 classes.jar），真正的实现在
  **`graphics-shapes-android-1.0.1.aar`**（88KB，含 classes.jar）。
- **如何验证官方库真的打进了 APK**：类被 R8 混淆后在 dex 里搜不到原类名，
  应查 `app/build/outputs/mapping/release/mapping.txt`。实测存在
  `androidx.graphics.shapes.Morph -> d3.k`、`RoundedPolygon -> d3.q`、
  `Cubic -> d3.d`、`LoadingIndicatorDefaults -> d0.f1`、`MaterialShapes -> d0.h1`，
  证明官方形状库确实在 APK 内被使用（而非谐波近似）。
- **想直接验证官方库的运行时行为**（比读源码更可靠）：用 `javac` + 反射写个 JVM 探针，
  classpath 需包含 graphics-shapes / material3 / kotlin-stdlib / compose ui-unit /
  ui-graphics / ui-geometry 的 classes.jar，以及
  `androidx.collection:collection-jvm` 的 jar（缺它会报 `FloatFloatPair` 找不到）。
  注意：涉及 inline class（Point/FloatFloatPair）的方法在 JVM 探针里**结果可能不可信**，
  只有直接返回 float 的（如 `asCubics()` 的 anchor 坐标）才可靠。
- ★ **不要用元素共享动画做跨页面转场**（id33 用户明确要求移除）：
  原本 `MainActivity` 包了 `SharedTransitionLayout`，设置页三个入口按钮用
  `sharedBounds` + `rememberSharedContentState` 与二级页 `BasePanelPage` 做共享元素过渡
  （MCGA 同款），代价是 `SharedTransitionScope` 与 `AnimatedVisibilityScope` 两个参数
  要沿着 6 个文件层层透传（`MainActivity` → `MainScreen` → `SettingPage` → 三个 Page
  → `BasePanelPage`），而且 `AnimatedVisibilityScope` 必须从 `composable {}` 的 `this`
  取（不能在 `HorizontalPager` 的 `PagerScope` 里取，那里 `this` 指向 `PagerScope`），
  心智负担很重。**现已全部删除，改为 NavHost 默认转场**，所有文件签名同步简化。
  `SplicedColumnGroup` 的 `content: List<@Composable (Shape) -> Unit>` 保留 ——
  它本来就是为了给条目传差异化圆角做 `clip`，与共享元素无关。
- `ActivityRecord#getStartingWindowType` 的签名各 Android 版本差异极大，
  **只按方法名 + 返回 int 匹配，判据只看返回值**：SNAPSHOT(1) → SPLASH_SCREEN(2)。
  不要按参数个数过滤，也不要把 NONE(0) 一起改（半透明 Activity 会闪）。
- ★ **用户可见文案一律走 `strings.xml`，禁止 Kotlin 硬编码**（id33 起的约定）：
  包括对话框按钮、Toast、状态占位（"检测中…"）等。专有名词（KernelSU / Magisk /
  APatch）不需要翻译，但仍要在资源 ID 与字面量之间留双通道 ——
  `RootInfo` 用 `@StringRes nameRes + nameLiteral` 双字段：
  识别成功走 literal，识别失败走资源。
  资源改动后跑 `gradle :app:compileReleaseKotlin --offline -q` 即可验证资源引用有效
  （空输出 = 通过），无需整包 assemble。
- ★ **`module.prop` 是"事实性"元数据，必须与 `build.gradle.kts` 同步**（id33）：
  LSPosed 管理器读的是 `module.prop` 里的 `version`/`versionCode`，与 app 的
  `versionName`/`versionCode` 是两套独立字段，容易忘记同步（id33 之前 module.prop 还停在
  0.1 / 4，app 已是 0.3 / 32）。
  作用域以 `scope.list` 为准，**不要在 `module.prop` 的注释里复述作用域** ——
  注释会和 `scope.list` 漂移（id33 之前注释写"已取消 system 框架 Hook"，
  但 `scope.list` 里明确有 `android`，热启动 hook 正是靠它）。
